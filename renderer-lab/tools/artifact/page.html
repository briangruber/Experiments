Culling on the GPU, one indirect draw

The question was what stops three.js reaching Unreal's quality now that TSL exists. The shading language turned out not to be the gap — the way work reaches the GPU is. This is a working prototype of the piece that's missing.

What three.js already ships

My first plan was to build temporal anti-aliasing. Reading the r184 source made that redundant — it's already there, and so is most of the post-processing stack people assume is missing. The gap is somewhere else entirely.

CapabilityStatusDetail
Temporal AA Ships TRAANode — velocity, depth, Halton jitter, neighbourhood clamp
Motion vectors Ships VelocityNode and an MRT velocity output
Screen-space effects Ships SSGI, SSR, GTAO, denoise, FSR1, SMAA, FXAA as TSL addons
Meshlet clusterizer Vendored meshopt_clusterizer is present — but nothing consumes it
Indirect draw plumbing Ships The backend calls drawIndexedIndirect; geometry.setIndirect() is public
Driving an indirect draw Missing No example or class in the library uses it. This prototype is that piece
GPU-side culling Missing BatchedMesh frustum-culls in a JavaScript loop, on the CPU
Cluster LOD Missing Buildable on the vendored clusterizer; the software rasteriser is not

So the shading language isn't the bottleneck, and neither is post-processing. What's missing is the submission architecture: three.js still walks the scene graph on the CPU and issues a draw call per object. That's what this attacks.

How the GPU path works

Four steps, and the CPU never learns how many objects are visible.

  1. 01

    Test every instance

    A compute pass checks each instance's bounding sphere against the six frustum planes — one thread per instance, no scene-graph walk.

  2. 02

    Compact the survivors

    Each visible instance claims a slot with a single atomicAdd and writes its index there, turning a sparse set into a dense list.

  3. 03

    Write the draw call's own arguments

    That same atomicAdd targets the instanceCount field of a WebGPU indirect draw-argument buffer. The count is never read back.

  4. 04

    Draw once

    One drawIndirect, with parameters produced on the GPU. The vertex stage reads the compacted list to recover each surviving instance's transform.

Four things that bite

All four were bugs in my own code first, and the second one is the reason the first survived a passing test suite.

The clip convention is not a constant

Extracting frustum planes from a projection matrix needs to know where the near plane sits in clip space — OpenGL puts it at z = -w, WebGPU at z = 0 — and the two forms differ by roughly the near distance. I assumed a WebGPU renderer implies the WebGPU form. It does not.

Camera.coordinateSystem starts as WebGL for every camera, and Renderer.render() flips it to WebGPU, rebuilding the projection matrix, the first time that camera is rendered. The same camera therefore hands you an OpenGL-form matrix before its first frame and a WebGPU-form one after. Hardcoding either is wrong half the time; the fix is to read the flag.

A test can inherit the bug it is testing for

The check above compared my planes against three's own Frustum — a genuinely independent implementation — but I passed it a hardcoded WebGPUCoordinateSystem. So the reference was mis-parameterised in exactly the way the code was wrong, the two agreed, and eight poses reported PASS while both were wrong.

What caught it was a different kind of check: take the eight corners of the drawn frustum wireframe and confirm each one lies inside all six extracted planes. It assumes no convention at all, so it had nothing to inherit. The test now drives coordinateSystem explicitly and runs every pose under both.

VelocityNode ignores positionNode

three's built-in motion vectors are derived from positionLocal and the object's model matrix, regardless of what the material's positionNode actually computes.

The GPU-driven path derives world position in the vertex shader from a storage buffer, so the built-in node sees one unit icosahedron at the origin and produces the same wrong motion for every instance. TRAA turns that into visible smearing. The replacement computes velocity from the same world position the vertex stage used, against an explicitly unjittered previous view-projection.

Readback rows are padded

WebGPU requires a texture-to-buffer copy's bytesPerRow to be a multiple of 256. Reading back a render target whose width times four is not, and treating the result as tightly packed, shears the image into diagonal streaks.

The frames above were captured at 1152 pixels wide precisely because 1152 × 4 = 4608 = 256 × 18. It is worth knowing before you conclude your renderer is broken.

What was actually verified

Every check below was deliberately broken first, to confirm it would notice. A test that can't fail isn't evidence — and as the previous section shows, one that can fail may still be asking the wrong question.

  • PASS Culling matches THREE.Frustum exactly across eight camera poses — set equality, not matching counts. Now run under both clip conventions, sixteen cases, with the reference following the camera's own flag. Reverting to a hardcoded convention fails half of them.
  • PASS All eight corners of the drawn frustum wireframe lie inside all six extracted planes, to within 1e-4. This is the check that assumes no convention, and the one that caught the bug the test above had inherited.
  • PASS The indirect path renders pixel-identically to the un-culled path, in a single draw call, on a frame checked not to be saturated — a fully covered frame would let a wrongly culled object hide behind its neighbours. Dropping every eighth instance fails on image mismatch.
  • SKIP The motion-vector comparison needs multi-target render targets, which produce no output in the container I built this in. The velocity fix is reasoned about and written, but not confirmed.
No performance numbers were measured. WebGPU canvas presentation is broken under SwiftShader in that container — the device is lost the moment a canvas context is configured. I confirmed it's environmental rather than a fault in the code: a plain WebGPU triangle with no three.js involved fails identically, while compute passes and offscreen render targets work fine. Which means the readouts above this text, running on your machine, are the first real measurement this prototype has had.

Where this goes

All three next steps are tractable on today's WebGPU. In order of value: HZB occlusion culling, which extends the existing compute pass with a depth pyramid rather than replacing it; multi-geometry batching, one indirect draw per geometry from a single dispatch, which is what makes this useful for real scenes rather than one repeated mesh; then cluster LOD on the clusterizer three already vendors.

Two things stay out of reach until the API grows. Nanite's software rasteriser needs 64-bit atomics, which WebGPU doesn't have. Lumen-class global illumination needs ray queries, which haven't shipped. Those are the real ceilings — not TSL.
